================================================================================
  一、总体评价
================================================================================

BBBus 是一个功能完整的 Windows 自动化按键工具，代码结构清晰，模块划分合理。
当前代码已具备良好的基础：线程安全有基本保护、Canvas 自绘 UI 体验良好、
配置持久化稳定。以下建议旨在提升正确性、可维护性和扩展性。

================================================================================
  二、高优先级（架构与正确性）
================================================================================

【P1-1】key_worker.py — 主键/副键互斥逻辑缺陷
  位置：key_worker.py 第 143-153 行
  问题：当副键满足发送条件时，走 if 分支只发副键，else 分支才发主键。
        这意味着副键会"吃掉"主键的发送周期，导致主键频率下降。
  建议：改为两个独立判断，主键始终发送，副键在满足间隔时额外发送。

  // 当前逻辑（有问题）
  if sub_key and (now - last_sub_send) * 1000 >= sub_key_interval:
      _send_key_to_window(hwnd, sub_vk)  // 只发副键，主键被跳过
  else:
      _send_key_to_window(hwnd, vk)       // 只发主键

  // 建议修改为
  _send_key_to_window(hwnd, vk)           // 主键始终发送
  if sub_key and (now - last_sub_send) * 1000 >= sub_key_interval:
      _send_key_to_window(hwnd, sub_vk)   // 副键额外发送
      last_sub_send = now

【P1-2】key_worker.py — 模块级缓存缺少线程锁
  位置：key_worker.py 第 16-21 行
  _proc_cache 和 _hwnd_cache 是模块级变量，被工作线程和主线程（通过
  get_running_processes）同时访问，没有任何锁保护。
  风险：虽然当前只有一个工作线程，但未来扩展或并发调用
        get_running_processes 时可能发生竞态条件。
  建议：为两个缓存添加 threading.Lock，或改用 queue/thread-local 存储。

【P1-3】key_worker.py — _find_window_by_process 枚举窗口时回调对象泄漏
  位置：key_worker.py 第 83 行
  每次调用 EnumWindows 时都创建新的 WNDENUMPROC 实例：
    user32.EnumWindows(WNDENUMPROC(enum_proc), 0)
  这会导致 C 回调对象不断创建，可能引起 GC 延迟回收或引用泄漏。
  建议：在模块级别预先创建回调对象，复用。
    _enum_callback = WNDENUMPROC(enum_proc)
    然后每次调用 user32.EnumWindows(_enum_callback, 0)

【P1-4】gui.py — 瞄准镜裸 except 吞没异常
  位置：gui.py 第 683 行
  except: 会捕获所有异常（包括 KeyboardInterrupt、SystemExit），而且静默吞没。
  建议：改为 except (psutil.NoSuchProcess, psutil.AccessDenied, Exception):
        至少记录异常信息以便调试。

【P1-5】logger.py — 每次写日志都打开/关闭文件
  位置：logger.py 第 33-35 行
  高频按键场景下（50ms 间隔），每秒最多 20 次文件打开/关闭操作，
  对磁盘 IO 和性能有明显影响。
  建议：保持文件句柄打开，定期 flush；或使用 logging 标准库的 FileHandler。

【P1-6】logger.py — 写入失败会导致工作线程崩溃
  位置：logger.py 第 34 行
  open(LOG_PATH, "a") 如果失败（磁盘满、权限不足），异常会直接传播到
  key_press_loop，导致按键循环终止。
  建议：在 log() 函数内捕获 IOError，静默降级。

================================================================================
  三、中优先级（可维护性与健壮性）
================================================================================

【P2-1】gui.py — BBBusApp 类过大（691 行）
  位置：gui.py 第 197-888 行
  BBBusApp 同时承担了：UI 构建、配置 IO、热键管理、进程对话框、瞄准镜、
  启停逻辑、窗口管理 等职责，违反单一职责原则。
  建议拆分：
    - ConfigManager    : 配置读取/写入/验证（从 config.py 扩展）
    - ProcessDialog    : 进程浏览对话框（独立类）
    - CrosshairOverlay : 瞄准镜选择器（独立类）
    - KeyLoopController: 工作线程生命周期管理
    - BBBusApp         : 主窗口，仅负责 UI 组装和事件路由

【P2-2】config.py — from_dict/to_dict 手动维护字段列表
  位置：config.py 第 30-57 行
  添加新字段需要在 3 个地方同步修改：@dataclass 类体、to_dict()、from_dict()。
  遗漏任何一个都会导致配置丢失或回退到默认值。
  建议：使用 dataclasses.asdict() + 类型注解自动序列化；
        或使用 Pydantic dataclass（带验证）。

【P2-3】config.py — 配置损坏时静默回退
  位置：config.py 第 66 行
  load_config() 在 JSON 解析失败时静默返回默认配置，用户不知道配置已损坏。
  建议：至少通过日志记录警告；或备份损坏文件后再重置。

【P2-4】gui.py — 配置与 UI 状态同步需要手动调用
  位置：gui.py 多处
  当前 _collect_config() 逐字段手动映射 StringVar → dict，_load_to_ui() 反向
  逐字段映射 AppConfig → StringVar。字段增删时容易遗漏。
  建议：使用双向绑定模式（如 descriptor 或 observable dict），
        让 UI 和配置自动同步。

【P2-5】hotkey_manager.py — 回调异常静默吞没
  位置：hotkey_manager.py 第 94 行
  except Exception: pass 让热键回调中的 bug 完全不可见。
  建议：至少 log 异常信息；或通过 tkinter 的 report_callback_exception 机制处理。

【P2-6】gui.py — 窗口关闭时 worker_thread.join(timeout=0.5) 可能不够
  位置：gui.py 第 887 行
  如果工作线程正在 sleep（最多 950ms），0.5 秒可能不够等待。
  建议：增加超时到 2 秒，或使用 stop_event.wait(0.1) 循环替代 sleep
        以提升响应速度。

【P2-7】缺少配置迁移机制
  位置：config.py 整体
  当前 config.json 没有版本字段。如果 V4.0 修改了字段名或默认值，老用户的
  配置文件无法自动迁移。
  建议：在 AppConfig 添加 version 字段；load_config 时检查版本并执行迁移。

================================================================================
  四、低优先级（代码质量与风格）
================================================================================

【P3-1】gui.py — psutil 重复 import
  位置：gui.py 第 496 行和第 632 行
  _on_pid_focusout 和 _target_window 各自在方法内部 import psutil，
  但 psutil 已在文件顶部通过 key_worker 间接可用。
  建议：统一在文件顶部 import psutil，避免重复导入。

【P3-2】代码路径解析模式重复
  位置：config.py 第 11-14 行、logger.py 第 11-14 行、gui.py 第 231-234 行
  getattr(sys, "frozen", False) 判断 + os.path.dirname 拼接的逻辑
  在 3 个文件中重复出现。
  建议：提取为公共工具函数，放在 utils.py：
    def get_base_path() -> str:
        if getattr(sys, "frozen", False):
            return os.path.dirname(sys.executable)
        return os.path.dirname(os.path.abspath(__file__))

【P3-3】_resize_all 在每次窗口 resize 时全量重绘
  位置：gui.py 第 513 行
  每次 Configure 事件都删除并重建所有 Canvas 元素，频繁调整窗口大小时性能
  较差。
  建议：添加防抖（debounce），100ms 内只执行一次；或使用 Canvas.coords()
        动态更新而非 delete + recreate。

【P3-4】vk_map.py — 按键映射不完整
  位置：vk_map.py 第 21-36 行
  缺少小键盘按键（numpad0-9, numpad+, numpad-, numpad*, numpad/）、
  常用符号键（, . / ; ' [ ] \ - =）、鼠标按键等。
  建议：补充完整映射表，参考 WinUser.h 的 VK_* 常量。

【P3-5】vk_map.py — _MOD_FLAGS 命名不当
  位置：vk_map.py 第 39 行
  以下划线开头的变量名暗示模块私有，但实际被 hotkey_manager.py 导入使用。
  建议：去掉前缀下划线，改为 MOD_FLAGS 或 MOD_VK_TABLE。

【P3-6】gui.py — _parse_int 默认值语义不清
  位置：gui.py 第 588 行
  函数签名 default=50，但在不同调用点传入不同的 default。如果某处忘记传参，
  会静默使用错误的默认值。
  建议：去掉默认值参数，改为必传；或拆分为 _parse_interval_min/_parse_interval_max。

【P3-7】main.py — 裸 except 吞异常
  位置：main.py 第 18 行
  except Exception: pass 会静默吞掉 DPI 初始化失败的异常。
  建议：至少 print 警告信息。

【P3-8】main.py — 使用已弃用的 DPI API
  位置：main.py 第 17 行
  SetProcessDpiAwareness(1) 在 Windows 10 1703+ 已弃用。
  建议：在 Windows 10+ 上使用 SetProcessDpiAwarenessContext(-4)；
        通过版本检测降级到旧 API。

【P3-9】gui.py — Canvas 缩放效果精度丢失
  位置：gui.py 第 484-489 行
  图标按钮的按下动画使用 cv.scale() 缩放 0.92，释放时用 1/0.92 还原。
  浮点除法可能产生微小精度误差，多次点击后图标逐渐偏移。
  建议：在 scale 之前保存原始坐标，释放时用原始坐标还原；
        或使用 move 代替 scale。

【P3-10】缺乏类型注解
  位置：全局
  大量函数缺少返回类型注解（如 _find_window_by_process 返回 Optional[int]），
  shared_config 是裸 dict，函数参数类型不明确。
  建议：逐步添加类型注解，至少为公共接口添加；引入 mypy 检查。

【P3-11】gui.py — 输入框占位符系统复杂
  位置：gui.py 第 413-448 行
  占位符通过闭包变量 ph_showing[0]、StringVar.trace_add、多重事件绑定实现。
  逻辑分散在 FocusIn/FocusOut/Key/VarWrite 四个回调中，理解成本高。
  建议：封装为 PlaceholderEntry 类，将占位符逻辑集中管理。
